# 前端设计与交互规范

目标不是给所有小程序套同一套 UI，而是把用户的参考或业务需求变成能实施、能对照的约定。使用 [项目交付模板](../assets/project-contract-template.md) 在应用仓库记录。

## 1. 先确定基线

记录参考文件/版本、已确认截图、逻辑视口、示例记录、日期/时区、当前页面和展开状态。用户最新确认优先于旧样机。数量或超时颜色不同，先排除数据与时钟变化，再判断视觉错误。

没有指定风格时，按使用场景选择信息密度与交互深度：查询服务突出状态与下一步；录入工具突出表单和错误反馈；工作台突出优先级与快速操作。风格库只作建议，不决定业务字段。

## 2. 提取设计变量与组件

- 颜色：页面底色、卡片、主要/次要文字、边线、强调、成功/警告/危险、禁用。状态不能只靠颜色区分。
- 文字：标题、正文、辅助与数字的字号/字重/行高；长标题的换行和截断；不要借未支持的 HTML 标签实现字重。
- 几何：页面边距、间距级别、卡片/按钮/标签圆角、边框、阴影、图标大小/描边、触控区。建议关键触控区不小于 44 个逻辑像素，视觉小图标可扩大透明命中区。
- 组件：按钮、筛选标签、搜索框、卡片、底栏、详情、编辑面板统一定义普通/按下/选中/禁用/加载态；是否共用组件按实际重复和行为一致性决定。

保留用户已确认的数值，不把建议当作强制主题。HTML 的逻辑 px、截图物理像素和 rpx 不混用；参考宽度为 W 时，内容尺寸可按 `px × 750 / W` 换算，并在目标设备验证。系统区域使用实际测量。

## 3. 写清交互而不是仅贴图

对每项关键动作记录：起始状态、触发、过渡、结果、取消/失败、是否持久化、返回位置。

| 对象 | 必须确定的问题 |
| --- | --- |
| 搜索/筛选 | 查询哪些字段？何时执行？计数基于全量还是筛选结果？跨页是否保留？ |
| 列表/详情 | 卡片与内部按钮是否独立响应？返回保留来源 tab、筛选和滚动吗？ |
| 编辑面板 | 新建/编辑初值、校验、保存中关闭规则、重复提交、脏数据取消、键盘避让 |
| 手势 | 横纵方向判定、触发阈值、取消、快滑、反向、多指、滚动冲突；有无点按替代入口 |
| 状态更新 | 立即反馈还是等待服务端？失败如何回滚？旧请求是否会覆盖新值？ |
| 日期/日历 | 业务时区、全天与定时、范围边界、跨午夜、月份切换、选中日期与筛选关系 |
| 图片/附件 | 占位、失败、替换/移除、裁切比例、上传进度、保存失败后的资源处理 |
| 删除 | 单条/关联范围、确认提示、部分失败、返回与恢复方式 |

未完成的交互必须标记，不能用静态层叠图或“已保存”提示冒充动作。

## 4. HTML 到原生小程序的高风险差异

- 原生导航和自定义导航择一；自定义导航根据状态栏与胶囊边界布局，处理底部安全区。不把假刘海、假状态栏、假更多按钮叠加到系统胶囊上。
- 检查 button 默认 margin、width、line-height、padding、伪元素边框与 flex 收缩。新增按钮、筛选标签、图标按钮分别重置，不能全局强制满宽。
- 自定义 TabBar 的容器宽度、内边距、选中指示器和安全区用同一坐标系；按实际可用宽度定位，不写死某机型截图偏移。键盘/抽屉显示时底栏策略明确。
- HTML 元素与 DOM/CSS 能力不假定直接存在于 WXML/WXSS。图标用兼容资源而非相似 Unicode 字符；复用已有已验证的图标系统。
- 共享样式和组件隔离一起核对；主题变量集中维护，避免层层追加全局覆盖与 `!important` 掩盖冲突。
- 页面隐藏/卸载后清理动画与监听；过期异步结果不写回已切换的记录或页面。

## 5. 验收证据

至少覆盖一个窄视口与一个常用视口、不同安全区、键盘弹出、长内容、空/加载/错误状态。记录实际尺寸与状态，不声称已测试未使用的设备。

视觉对照需同视口、同数据、同日期、同交互状态；核对结构、对齐、间距、字重、图标、底栏和系统区域。复杂手势另做触摸验证，截图本身不能证明手感。

把结果分为已通过、待确认、未验证。模板静态检查与 JS 单测不能证明真实渲染；用户禁止浏览器时遵守限制，使用允许的开发者工具/提供的截图或明确缺少界面验收。不要因此谎称“一模一样”。
