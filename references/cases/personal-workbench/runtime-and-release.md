## 凭证以当前代码为准

当前三个运行秘密见 `.env.example`：

- `JINSHUJU_ACCESS_TOKEN`：金数据 Token 原文，不加 `Bearer `；请求代码加前缀。
- `WORKBENCH_PASSPHRASE_HASH`：由 `server/auth.js` 的 `hashPassphrase` 生成的加盐 scrypt 值。
- `WORKBENCH_SESSION_SECRET`：独立签名密钥，各运行副本一致。

环境 ID、AppID、服务名和 Table Token 可以存源码。真实秘密不放前端、Git、聊天、命令行参数或日志。确认变量保存和运行版本载入是两件事；只展示配置是否存在、状态码等非敏感证据。

口令方案已替换旧 OpenID 名单。使用 `docs/passphrase-access.md` 和实际 `server/auth.js`，不要照 `docs/code-review-2026-09-05.md` 的历史条目补名单。持有口令者共享同一份数据，不能将其描述为多租户权限隔离。业务请求使用签名会话；缺配置拒绝请求，不能靠客户端自填 AppID/OpenID 绕过。

锁定清理本机凭证和业务缓存，不等于吊销已经复制的服务端凭证；轮换秘密要考虑所有副本和旧版本流量。进程内限流不等于多副本共享限流。云存储/图片链接的规则独立于业务口令。按本次任务需要核对，不把每次样式修改扩成认证重构。

## 发布前确认实际触发方式

仓库历史中既有 `main` 推送触发流水线，也有手动上传后端的交接。**仅靠 README 或旧截图无法判断现在是否仍自动部署。** 推送前核实当前监听分支和用户授权；未知时停在本地交付，不能先 push 再观察。不要新增一个所谓必填运行变量来冒充已检查过的控制台配置。

- 当前确认为流水线时：一次已获授权的 push 对应一次触发，之后观察该流水线和它创建的精确版本；不要再叠加 CLI、手工触发或空提交。
- 当前确认为手动时：已有流水线不能同时监听本次变更；在授权范围内完成一次部署，并核对这次操作返回的版本。
- 部署失败先读构建日志、目标目录、端口和版本配置。结果不明先查状态，不能重复执行带副作用的动作来确认是否成功。

构建成功不等于正在服务。记录触发关联、目标版本、稳定状态与实际流量切换；无法关联提交和版本时明确“尚未确认线上版本”。环境变量报错不靠“再推一次肯定好”解决。

## 小程序上传与后端是两条交付链路

只有用户选 CI/CLI 上传时才需要小程序上传私钥；开发者工具手动上传不应要求用户在聊天提供私钥。AppID 不代替上传授权。

前端上传不会自动部署后端，Git push 是否触发后端由已核实的流水线决定。前后端协议改变时（如新增口令登录），先验证并部署兼容后端，再上传配套前端；保留回退方案。小程序编译、预览、开发上传、体验、提交审核与正式发布分别报告，不能混称“上线完成”。

## 本地检查与交验

从工作仓库根目录执行 `node --test tests/*.test.js`。测试使用 Node 内置模块与模拟上游，认证路由测试需要临时监听 `127.0.0.1`；遇 `listen EPERM` 先按工具权限机制申请仅执行本地测试，不删除测试或改生产代码放行。无需真实 Token、真实口令或真实表写入。

有界面工具权限时进行开发者工具编译、模拟器与真机适配验收。用户禁止浏览器时不用浏览器；拿不到运行界面就明确视觉未验证。提交前检查 diff，未获验收/推送授权时只留下本地可审查文件。不要把本次同步、测试或文档更新写成已经更新线上 Skill。
