## 将真实交付信息变成用户操作

| 步骤 | 对用户的引导示例 | 助手承担的工作与推进条件 |
| --- | --- | --- |
| 用途 | “我理解你想把工作项目、生活计划和随笔放在一个地方。这个工作台只有你用，还是其他人也需要进入？” | 将访问选择记入需求，解释不同访问方式的结果；不直接套用案例共享口令。 |
| 页面 | “先看工作页：新建一个项目，再添加一个任务，看看这些信息是否够用。” | 做好首页/工作/生活/随笔及关键动作，用户确认后才定基线；随笔是完整月历索引，点击日期查看记录。 |
| 数据表 | “这些内容拟分别放在工作项目、项目任务、个人计划、随笔四张表中。我把每张表的栏目列好了。” | 展示可读字段方案，任务关联项目用稳定标识；检查当前 MCP，在授权范围内建表并读回。案例按项目名称关联是限制，不应照抄。 |
| 导入预览 | “我已准备好文件。请在微信开发者工具导入【实际目录】，使用你的 AppID。编译后应该看到【本版本入口页】。” | 核实实际目录中的 `project.config.json`，该案例 `miniprogramRoot` 为 `miniprogram/`；助手填写配置和解决编译问题，不让用户修改 JS。 |
| 后端配置 | “现在配置负责保存数据的服务。先选已核实的环境和服务，这一步只核对构建信息。” | 生成下面的填写卡，逐次配置构建信息与运行秘密，确认当前发布触发方式；不要一次把全部控制台任务交给用户。 |
| 真实保存 | “服务就绪后，我们新建一条测试计划，再退出重进看它是否还在。” | 在授权测试范围内检查持久化、字段映射和错误；随后测试图片随笔，不能凭一条读取请求就声称全部 CRUD 正常。 |
| 真机与交付 | “接下来用手机体验工作、生活和随笔。效果确认后再把本次版本设为体验版。” | 给出实际预览结果，处理设备问题，核对用户本次终点；后端发布、上传、体验、审核、正式发布分别记录。 |

## 本案例的填写卡如何产生

这些值来自本次读取的源码。它们只是解释方法，不能证明线上已经这样配置：

| 控制台项目 | 源码证据与交给用户的说明 |
| --- | --- |
| 构建目录 | 仓库方式为 `server`；后端 ZIP 方式为包根目录，助手必须先核对包内容。 |
| Dockerfile | 相对于上述构建目录填写 `Dockerfile`。 |
| 监听端口 | 当前 Dockerfile 中 `PORT` 与 `EXPOSE` 为 `80`，按这个代码版本填写。 |
| 构建文件 | Dockerfile 复制 `package.json`、`index.js`、`auth.js`；助手检查打包文件齐全，秘密文件不进入构建包。 |
| 运行秘密 | 当前案例需要 `JINSHUJU_ACCESS_TOKEN`、`WORKBENCH_PASSPHRASE_HASH`、`WORKBENCH_SESSION_SECRET`；分别给用户说明安全配置位置，生成过程由助手准备，不要求用户计算哈希。 |
| 环境与服务 | 维护案例时核对 [运行与发布](runtime-and-release.md) 中的既有资源；新应用使用用户自己的资源，助手据此更新小程序配置。 |

不能只告诉用户“配置三个环境变量就行”。下一步需要验证配置是否被当前运行版本载入、请求是否被正确路由、身份和读写是否正常。

## 案例暴露出的引导断点

- README 是开发部署交接，并不包含从注册账号、体验样机到审核发布的完整新手步骤；通用 Skill 必须补上前后两端的引导。
- 历史代码评审里的 OpenID 名单已被后来的共享口令方案替换。助手先核对当前实现，再告诉用户准备什么，不能混用两份说明。
- 文档明确前后端需配套更新。本次后端未验证时，即使前端上传成功，也要把用户停留在正确的联调步骤，不能交付一个无法登录的“成品”。
- “已填变量”“构建通过”“新版本承接流量”“真机能保存”是不同状态，每一步需要给用户对应的成功标志。
- 代码及说明中的自动测试通过次数属于历史记录；新工作必须运行实际需要的验证，不能继承为当下结果。
