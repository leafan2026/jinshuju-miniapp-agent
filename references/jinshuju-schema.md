# 金数据表结构与字段映射

## 分清提议与实际绑定

从业务实体、页面字段和权限需求提出模型。新应用可以先做未绑定的字段方案与假数据；已有应用先读取现有表结构，避免覆盖历史记录。不要默认每个 UI 卡片一张表，派生计数/进度通常不必重复持久化。

管理操作先发现当前会话的金数据 MCP 工具及输入 schema。用户已有明确建表/写数据授权时，在其范围内执行并读回；未授权的结构变化先展示表名、字段、用途及影响。删除、字段类型变化、迁移尤其核对目标及恢复办法。

MCP 不可用/未授权时，继续不依赖真实连接的工作并列出待绑定项。不得编造工具名称、字段 key、表 ID、选项编码或创建结果；也不要求用户为建表启动另一个 Agent 框架。

## 数据契约

用 [字段映射模板](field-mapping-template.md) 记录实际结构和观测来源；[字段形态参考](jinshuju-field-types.md) 只帮助设计，不是上游返回 schema。

每张表明确：
- 实体与稳定定位字段、业务唯一性、关联方式；名称可变时不要直接当永久外键。
- 前端业务字段 → 实际字段名/key/类型/选项；读与写的转换、空值、单位、时区。
- 哪类角色可读写哪些记录；权限由服务端核验，不只靠前端筛选。
- 查询、分页、排序、过滤、创建/修改/删除与错误返回；需要写入的应用不能默认只有 GET。
- 多表操作的部分失败处理；未验证的事务、唯一性或关联能力明确标为应用层待实现。

普通更新仅发送改动字段。假数据导入只在授权的新表/测试范围内进行，导入前核对已有记录和幂等策略；真实读取失败不意味着可以重导数据。

## 两条接入链路

Agent 使用会话 MCP 建表/核验。云托管服务使用自己的受控凭证和已验证的接口契约；可选择合适的金数据 API 或 MCP，记录方法、返回形态和错误处理。案例的读取 API、写入 MCP 与附件 API 是一个实现方案，不是未经核验即可复制的万能工具集。

完成后读回结构/记录，更新映射文档与适配测试。最终交给小程序与云托管实现的是已核实的契约，而不只是表名清单。
