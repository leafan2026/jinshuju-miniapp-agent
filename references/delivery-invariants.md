# 项目日志

本文件记录会影响后续开发判断的可复用问题、原因、解决方案与不变量；它不是部署流水账，不记录版本号、提交号、PR 或发布结果。修改部署、云托管、上传或凭证处理前必须阅读。

## 2026-09-04

### 1. 云托管工作流与 CLI 不能同时成为同一分支的发布触发器

- 问题：云托管已监听仓库分支的推送时，Agent 又调用 CLI 部署，会让同一提交创建两个版本，导致版本归属和流量验证混乱。
- 原因：发布模式未作为环境配置和工具前置条件维护，Agent 将 CLI 误当作验证流水线的手段。
- 解决：使用必填的 `WXCLOUD_DEPLOY_MODE`。`pipeline` 模式下推送是唯一触发器，`deploy_cloudrun` 在审批前拒绝执行；`manual` 模式下先确认不存在监听该分支的自动工作流，才允许一次 CLI 部署。
- 后续约束：一个服务/分支只能选择一个触发器。不能额外调用 CLI、手动构建或重试性部署来确认流水线结果。

### 2. 部署成功必须绑定精确候选版本

- 问题：仅凭版本备注、创建时间或服务当前状态，容易把历史版本误认为这次推送/部署的结果。
- 原因：云托管版本通常不能直接提供源代码提交标识，模糊匹配不足以证明版本归属。
- 解决：流水线在触发前记录已有版本集合，触发后只验证新出现的版本；手动模式只验证本次创建的版本。完成条件为目标版本稳定且承接预期流量。
- 后续约束：无法识别精确候选时只能报告等待或失败，不得用历史版本、相同备注或再次部署代替验证。

### 3. 云托管配置和秘密是同一份配置契约

- 问题：环境 id、发布模式、Access Token 或上传密钥若分散维护，部署和运行会使用不一致的配置；秘密若被打印或作为参数拼接，也会泄露或截断。
- 解决：统一从受控环境变量读取配置；秘密不进入代码、小程序包、命令行、工具输出或日志。变更前后仅校验是否存在及非敏感元数据。
- 后续约束：更换环境、仓库分支或发布模式时必须一并复核 `WXCLOUD_ENV_ID`、`WXCLOUD_DEPLOY_MODE`、工作流监听范围和所需凭证。
