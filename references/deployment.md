# 开发、云托管部署与小程序上传

## 运行架构与配置

微信小程序 `wx.cloud.callContainer` → 微信云托管服务 → 金数据 Tables。不要以部署云函数、`callFunction` 或额外 Agent 运行时替代这个链路。

核对小程序环境 ID、服务名、请求路径与实际目标服务。容器监听地址/端口、Dockerfile、构建上下文及 COPY 依赖保持一致；使用案例源码时先检查其实际设置，不把案例端口强制应用于所有项目。

金数据 Access Token 从服务端受控秘密配置读取，请求时加 Bearer 前缀。AppID、环境 ID、服务名、仅用作资源标识的 Table Token 可以入库；认证方案可能另需哈希、会话密钥等，以本应用代码为准。不能笼统说“只需要金数据 Token”。

MCP 授权、环境变量已保存、正在服务的版本已载入配置是三件事。只核对变量是否存在/非空及非敏感状态，不输出秘密值。网络出口与白名单按 [接入准备](collect-requirements.md) 核实。

## 发布触发方式

执行前核实目标仓库、分支、环境、服务、构建目录、当前监听方式与用户授权。未知时停在本地交付。部署模式记录在项目交付说明即可；除非项目确实实现并读取，不要求添加 `WXCLOUD_DEPLOY_MODE` 来冒充控制台校验。

- 流水线：一次已授权的 push 或明确的工作流触发后，观察该次运行及其产物；不要额外叠加 CLI/手动构建来“确认”成功。
- 手动：确认本次变更不会同时由自动监听重复发布，使用获授权的控制台、ZIP 或 CLI 方式，记录该次操作返回的版本。
- 失败/结果不明：先查状态、构建日志和流量，不盲目重发或制造空提交；重试需依据故障原因与已有授权范围。
- 切换触发方式需明确授权和对应配置，不把临时绕路当作模式切换。

将提交/源码包与本次构建、目标版本关联，再核验稳定状态及预期流量。版本集合前后差异只能帮助定位候选；多个候选时不能靠时间、标题或备注认定归属。拿不到关联证据就标明“线上版本未确认”。

## 小程序交付是另一条链路

- 开发者工具：用用户的 AppID 导入应用项目，编译和预览；用户选择自己上传时提供项目路径和版本说明，不要求向 Agent 交私钥。
- CI/CLI：仅在选择该路径时使用受控上传私钥、AppID、版本与运行环境权限。参数依据实际安装工具核实；秘密内容不进入命令参数和日志。
- 预览二维码、开发上传、体验版、提交审核、正式发布分别核验并报告，不能互相替代。

前端上传不会部署后端；Git push 是否触发后端由流水线决定。协议变化先验证兼容性和回退方案，按依赖顺序发布。需要展示二维码时必须取得真实预览结果，不能生成示意二维码冒充可测试开发版。
