# 一步一步带用户完成小程序

## 如何使用这份手册

这是新建应用的默认引导顺序。已有项目先核对实际文件、已确认需求与交付记录，跳过已完成步骤；只改界面或只建表的请求只走相关部分。阶段内能独立推进的代码、测试由助手完成，不让用户逐条确认实现细节。

对用户用业务语言：Table 可解释为“在金数据里保存这类信息的数据表”，云托管可解释为“小程序安全读写金数据的后端服务”，MCP 可解释为“让当前助手操作金数据的连接”。需要输入平台名称时保留准确原名，不让用户先学习这些术语。

每次交接可用三四句自然语言说明：

> 现在进行到【当前步骤】。我已完成【有证据的成果】。这一步需要你【一项操作/一到两个问题】。完成后应该看到【结果】；接下来我会【下一步】。

不要机械重复格式，也不要把内部实现表整份交给用户。需要用户回复的步骤等待回复；仍可进行不依赖该回复的工作。遇到报错记录原始现象并在本步骤解决。

## 第 1 步：明确要做什么

**先问什么：**“这个小程序主要给谁用？你希望他们打开后最先完成哪件事？”用户已经说明时直接复述理解，问剩余的一项。随后逐次确定第一版功能、谁能看/改哪些内容、有没有现成样式或数据。

**助手完成：**将回答整理成简短页面与流程提案，说明哪些是第一版、哪些暂缓；核实用户给的文件。为应用选定实际工作目录，有明确目录就沿用；已有项目核对 remote 与未提交改动，Skill 安装目录不作为业务输出目录。

**用户只需决定：**功能范围和访问范围。不要让用户设计数据库、指定技术栈或一开始准备所有密钥。

**进入下一步：**双方对第一版用途、主要页面、访问范围达成一致。需求参考见 [collect-requirements.md](collect-requirements.md)。

## 第 2 步：把页面和交互做出来

**助手完成：**有参考先提取布局与动作；没有参考提出一个适合业务的设计方向，用真实感假数据做可操作的样机，提供实际可打开的文件。按 [frontend-demo.md](frontend-demo.md) 和 [design-spec.md](design-spec.md) 验证所需流程，不能让按钮仅弹一句“成功”。

**请用户体验：**一次选一条核心路径，例如“打开工作 → 新建项目 → 添加任务 → 修改任务 → 返回”。下一轮再看生活计划、随笔等其他关键流程。询问看得懂什么、找不到什么和哪里不符合日常习惯，而不是要求用户审 CSS。

**确认产物：**用户接受的页面与交互基线、字段含义、后续待改项。明确当前是假数据、保存是否会在刷新后丢失。

**进入下一步：**核心路径已能演示，用户接受方向。新反馈修改基线，不拿旧原型覆盖已确认效果；已给成品时直接核对即可，不强行重画。

## 第 3 步：连接金数据，确认并创建数据表

**先由助手检查：**当前会话有没有可调用的金数据 MCP，是否已授权，能否发现本次所需的表结构/数据能力。连接存在就直接使用；不要先问用户要 Token，也不能因 Skill 自身没有连接代码就断言当前会话没连接。

**如果未连接：**先核对当前使用工具的连接入口和金数据官方接入说明，再只引导完成该连接。说明在哪里打开连接设置、需要选哪项、授权完成的迹象；需要 Token 时引导在金数据后台创建并放入宿主的安全配置，完整 Token 仅创建时展示一次。未核实的服务地址、认证流程和工具名不写成确定配置。Skill 本身不安装或保证 MCP；没有可用连接入口时明确阻塞原因和解除办法，继续准备表结构与模拟实现，真实建表记为未完成。不要转去启动 Eve、选择模型提供商或配置无关平台。

**助手完成：**把样机数据翻译成用户读得懂的表格：“保存哪类信息、有哪些栏目、和哪张表关联”。同时维护真实字段 key、类型、选项、分页和权限映射，用户无需手工填写这些技术字段。需要改结构时按当前工具能力提出方案；用户确认并授权后创建，逐表读回核验。已有授权不重复请求。

**用户只需确认：**分类与字段是否符合业务，是否允许本次建表/改表。示例数据导入单独说明范围，已有真实表不自动填充假数据。MCP 未提供建表能力时如实说明，给出当下支持的操作方案，不编造调用。

**进入下一步：**有可核实的表和映射；如暂时缺连接，可先进行明确标记为模拟数据的小程序预览。细节见 [jinshuju-schema.md](jinshuju-schema.md)。助手建表成功与后端运行凭证就绪分开记录。

## 第 4 步：在微信开发者工具里预览

**到这一步再问：**是否已有微信小程序账号、自己的 AppID 和可登录的微信开发者工具。没有账号时，按当前微信官方指引分次引导选择适合用途的账号主体、注册与取得 AppID；认证、类目、能力和费用要求核实后说明。本人扫码、身份验证由用户完成。

**助手完成：**将已确认设计实现为小程序，生成正确的项目配置并完成可在本地运行的检查。依照 [implementation.md](implementation.md) 实现数据适配与错误反馈；后端未接通时提供清楚标记的模拟预览，生产配置不允许静默回退到假数据。

**交给用户的操作必须具体：**

1. 打开已安装且已登录的微信开发者工具，使用其当前“导入项目”入口。
2. 给出本次生成的实际项目绝对路径，明确选择包含 `project.config.json` 的目录；助手已按真实结构填写 `miniprogramRoot`。不要给用户案例目录或泛指“项目根目录”。
3. 使用用户自己的 AppID，核对编译后应出现的首个页面，再沿样机核心路径操作。

一次只讲当前需要的操作；工具界面与上述入口不同时按实际界面调整。导入失败先查目录、AppID 和开发权限，编译失败由助手分析错误和修改代码。

**进入下一步：**开发者工具编译及主要页面可用。记录哪些已检查、哪些仍为模拟数据；这不是后端联调成功或正式发布。

## 第 5 步：配置云托管，让数据真正保存到金数据

**到这一步再准备：**用户自己的云托管环境、服务、受控运行凭证。先查已有资源，有可沿用的就核对后使用。没有资源时，按当前官方界面引导创建；涉及新服务费用时把具体选择和费用依据交给用户决定。

**助手先做好：**可信后端、身份与访问规则、Dockerfile、配置示例及构建检查。根据实际代码生成本应用的“控制台填写卡”，用户不用猜值或编辑代码：

| 要填写的项目 | 助手给出的内容 |
| --- | --- |
| 目标环境与服务 | 已核实的本应用标识；新建则先完成创建并读回 |
| 代码来源与分支/上传包 | 本次应用仓库和分支，或已检查的部署包路径 |
| 构建目录 / Dockerfile / 端口 | 从实际部署包与代码读取的值；相对哪个根目录写明 |
| 普通配置 | 名称与已核实的值；助手同步修改小程序环境与服务配置 |
| 秘密配置 | 仅列变量名、作用、获取/安全输入位置以及就绪状态 |
| 发布方式 | 当前服务是否监听仓库推送，本次唯一触发方式 |

这张卡只列当前应用使用的字段。共享口令、会话签名等若由业务方案选定，助手提供安全生成/配置方式，不让用户手算哈希，也不复制案例的秘密。金数据运行 Token 的请求头使用 Bearer，服务端所需网络权限按实际环境核实。

**引导用户操作：**分次完成选择服务、填构建信息、填受控变量、发布前检查。每次说清当前页面要填哪几项；无法操作平台时提供经核实的当前入口和填写卡。变量已保存不等于运行版本已载入，助手核验实际请求与版本状态。

**部署动作：**依照 [deployment.md](deployment.md) 和 [delivery-invariants.md](delivery-invariants.md)，核对本次授权后只触发一次；已监听推送时不另发 CLI。构建失败读对应日志修复，结果不明先查状态。

**进入下一步：**目标版本稳定且承接预期流量，小程序能真实读取；在授权测试范围内新增/编辑并重新读取后结果仍在。失败保留原因，不能把“数据全零”当正常空表。临时测试数据是否清理由事先约定范围决定。

## 第 6 步：真机验收

**助手完成：**准备与业务相关的简短体验路线，逐项核验数据、界面与错误反馈。获取实际预览结果；需要用户扫码或操作者无真机能力时明确分工。

**请用户一次测试一条路线：**例如新增项目和任务 → 改优先级 → 完成后返回；随后新建生活计划；再新增带图随笔、换月份查看、编辑正文。检查重新打开后的数据，确认保存不是只在当前页面有效。删除只使用授权测试记录。

**分别记录：**开发者工具编译、真机显示/手势、真实读写、访问限制。测试通过不自动证明全部设备和线上功能已验收；报错由助手继续修，不把整套日志交给用户自行排查。

**进入下一步：**用户接受本次效果，或已明确限定可交付范围与待改项。

## 第 7 步：交付体验版，按需要审核与发布

**先确定本次终点：**只要预览、给指定人员体验，还是申请正式发布；已有明确要求则直接沿用。根据目标逐次准备当前平台要求的信息与权限，不把完整上线资料作为做样机的前提。

**助手完成：**版本说明和本次实际项目位置。开发者工具已登录时可引导手动上传；只有选 CI/CLI 才准备上传密钥。上传后引导在微信公众平台对应版本管理入口找到本次版本，按当前规则配置体验权限；审核所需类目、隐私说明等根据本应用实际功能核对并协助填写，发布动作依既有授权执行。

**用户操作：**本人才能完成的扫码、账号权限、资料确认或平台提交。一次只给当前动作及结果检查；审核结果受平台决定，尚未通过就记录“审核中/待处理”，不能说已上线。

**交付结果：**明确“小程序处于哪个阶段、后端哪个版本在运行、业务数据保存在什么表、后续如何修改需求”。保留代码位置、配置位置（无秘密值）、回退办法和未完成项。

## 中断后如何继续

在应用的项目交付记录保留当前步骤与子步骤、用户最新确认、已完成证据、待用户动作、唯一下一步。用户说“继续”时先核实这些状态，再推进；不要重新问已经提供的 AppID、从头重做原型或重复建表。

连接缺失只阻塞真实表操作，平台权限缺失只阻塞对应预览/发布。用户明确选择先等连接时尊重该选择。工具报错不改成让用户启动另一套运行框架。

## 用案例检验引导是否可执行

阅读 [个人工作台带搭示例](cases/personal-workbench/guided-walkthrough.md)，检查新用户是否知道当下只需做什么。案例的四张表、AppID、端口、服务和口令都是具体选择；新应用的值由实际需求与代码产生。
